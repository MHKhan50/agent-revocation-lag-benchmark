# RevocationLag: A Synthetic Benchmark for Dynamic Agent Permissions

**Research area:** Agentic AI security, runtime authorization, behavioural assurance
**Version:** 1.0.0 — 27 October 2026
**Runtime:** Python 3.9.6+; standard library only
**Cost:** No GPU, paid API, model download, or Ollama call required

## Research question
How does authorization-check granularity affect unauthorized side effects after a tool permission is revoked during a multi-step agent workflow, and what control-event overhead accompanies each strategy?

This is a transparent *policy simulator*, not a test of an LLM's behaviour and not evidence of real-world agent security. It extends a static tool-policy benchmark with a distinct temporal dimension: a capability is valid at workflow start and is revoked before a later action.

## Run on your Mac
After unzipping into `~/Downloads`, run:

```bash
cd ~/Downloads/agent-revocation-lag-benchmark && python3 run_benchmark.py && python3 -m unittest discover -s tests -v
```

No `pip install` is needed. The command regenerates the 1,800-row dataset, evaluates all policies on identical traces, writes CSV/JSON metrics, creates an SVG graph, refreshes the article's results table, and runs tests.

To regenerate only the data: `python3 generate_dataset.py`
To regenerate the graph from the summary CSV: `python3 plot_results.py`

## Compared policies
1. `check_once`: check the capability at workflow start, then trust cached authorization.
2. `periodic_3`: re-check every three action positions, including position zero.
3. `per_sensitive`: check immediately before each sensitive action.
4. `push_revoke`: check at workflow start and receive an idealized instantaneous revocation notification.

The event-notification strategy is a deliberately strong baseline. Real systems can lose, delay, duplicate, or misorder events; this simulator does not model those failures.

## Metrics
- **Unauthorized side-effect rate:** executed post-revocation sensitive actions / all post-revocation sensitive-action opportunities.
- **Revoked-action block rate:** blocked post-revocation sensitive actions / all such opportunities.
- **Authorized-work completion:** executed actions that remain authorized / all actions that remain authorized.
- **Control events per episode:** authorization checks plus revocation notifications. This is a proxy for control overhead, not measured latency or monetary cost.
- **Episodes with any unauthorized side effect.**

Each of the 1,800 generated scenarios has a revocation event and at least one sensitive action after it. Fixed seeds: 17, 29, and 43; 600 scenarios per seed.

## Reproducibility and limits
- Data are synthetic and generated by included code; there is no external dataset.
- A single capability and fixed action plan are modelled. No LLM is called, no external tool is contacted, and no prompt injection, network failure, concurrent request, or sandbox escape is tested.
- The idealized event-notification policy assumes perfect delivery.
- Results describe the simulator's assumptions only; do not report them as real-world incident rates or general claims about commercial agents.
- A claim of research novelty requires a broader literature review. This package offers a reproducible research question and baseline, not proof that the question has never been studied.
